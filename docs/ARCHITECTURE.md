# Architecture

A modular monolith hosts one Spring Boot application and one PostgreSQL database; the React client uses same-origin `/api` and future `/ws` via Nginx. PostgreSQL is authoritative. Docker Compose waits for database health, a successful dedicated Flyway migration and backend readiness, in that order. Actuator exposes health probes; JPA validates instead of creating schema. Flyway is not an application dependency and runs only in the migration container.

Planned backend features: `auth` (identity and access), `event` (event state), `participant` (participant identity), `draw` (selection), `wheel` (prizes), `quiz` (Mohammed's ownership), `notification` (notifications); `common` holds shared errors, `config` infrastructure configuration. These are boundaries, not implemented services. Planned frontend boundaries are auth, participant, admin, draw, wheel, quiz; shared UI, layouts, hooks, services, styles, assets and types support them. Empty feature folders are not tracked until they contain work.

Authentication uses Spring Security, BCrypt and PostgreSQL-backed Spring Session JDBC with Flyway-owned tables. An administrator bootstrap is serialized with a PostgreSQL transaction advisory lock. Security contexts use a serializable principal without a password hash after authentication. Sessions can be shared across instances without sticky routing. JWT is not used. CSRF is required on state-changing requests, including login and logout. Default cookie flags are HttpOnly, SameSite=Lax, and Secure; the dev profile permits HTTP. All unapproved routes are denied. No WebSocket endpoint exists yet.

The login limiter is bounded and instance-local, keyed on the direct peer address, not forwarded headers. It counts attempts within a fixed window and resets on success; coordinated limiting and trusted proxy configuration must be designed before multi-instance production. Behind a proxy, all clients may share a bucket. Deploy with HTTPS and the prod profile.
